# Bounded repair and independent verification

A review can finish with actionable findings. Repair happens only within the user's requested scope; preserve the distinction between source edits, target application, conversation/API effects, deployment and sharing. Carry existing permissions forward instead of repeating approvals at every handoff.

For authorized findings, read the bundled [Artemis Developer](../../artemis-developer/SKILL.md). Pass the confirmed target/context, design and source hashes, original finding IDs, causal evidence/confidence, expected outcomes, permitted edits/effects, relevant constraints and verification scenarios. Give a repair-only assignment and retain verification ownership here. Developer must return its changed snapshot, diff, checks, self-tests, unresolved issues and any live read-back evidence; it must not recursively invoke this same review while the coordinator is awaiting its repair.

If the build started in Developer, an independent review assignment first returns findings to that build coordinator. Do not start a second Developer or repair cycle unless the coordinator explicitly assigned that responsibility. Reuse the existing run budget and authorization across the handoff; a skill switch does not create a new allowance. Prefer a separate reviewer agent for independent acceptance; if unavailable, disclose that the same agent performed both roles.

Preserve baseline files and make edits in the agreed working copy. Developer follows its current platform contract: guarded edits for a normal resource change, validated/previewed import when a whole package is appropriate, live drift reconciliation and read-back. A local hash manifest is not an atomic write guard. Do not require whole-project import for every fix or replay a timed-out write without reconciling its outcome. Deployment/promotion needs explicit authority.

Recommend native ABL controls and supported HTTP/API transformations for avoidable script logic. Reasoning/hybrid or routing changes must follow the confirmed design and actual capability evidence. A Code Tool or material architecture exception follows Developer's compact architecture confirmation, carrying prior explicit approval where still applicable. Do not weaken security, business acceptance or experience merely to reduce response time.

Default to one repair batch and one linked verification run unless the user grants another bounded scope. Establish the verification allowance in the repair plan, sharing any existing remaining allowance unless the user has authorized a separate one. New run IDs preserve lineage, not automatic permission for more tests. After the cap, report still-failing findings and next options.

Verify the exact changed snapshot independently. Reproduce the original scenario plus affected passing controls with comparable target/channel/setup; preserve original evidence and scenario IDs. Check business effects/status, not just a success utterance. Compare useful response/task timing and user effort together. Developer's test evidence may guide this work but cannot substitute for independent observations.

Only mark a finding Verified when its specified criteria are supported on the changed snapshot. Use Changed awaiting verification if runtime/channel access is missing, Still failing for reproduced failures, or Deferred with the reason. If new backend state or other users' changes make rollback unsafe, follow the agreed rollback scope rather than blindly importing the older export. Return a concise verified/remaining list and linked evidence. No public ticket, external message or report sharing is implied by local report creation.
